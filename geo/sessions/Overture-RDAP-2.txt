Project status
We are building an accurate geotargeting system.
A.	Targeting by DMA works.
B.	[Priority 1] For ZIP-code-to-IP-address translation, we are using landmarks (businesses, local government offices, schools, universities, libraries that host their webservers on-premises), currently from Overture (stored in table ovt_places_usa) but soon also from other sources, mainly Foursquare. However, static on-premises IP addresses, which must stay with the customer, are assigned through different ranges from dynamically issued (DHCP) IP addresses, which are often automatically moved to other geographic locations in the carrier’s footprint. But for each geographic location, the static and dynamic IP addresses are routed together. I propose the following algorithm (critique if necessary):
1.	For each ovt_places_usa.onpremises=true address, use mtr to find the carrier node immediately adjacent to customer premises equipment (CPE). The penultimate node usually, but not always, has a domain name in one of the carrier’s domains; when it does not, the CPE often has a domain name in the customer’s domain; when neither the last carrier node not the CPE have domain names, it is usually safe to assume that the penultimate node is the last carrier node before CPE.
2.	For each ip-api.com–probed address, obtain the carrier node immediately adjacent to CPE.
3.	If that node matches one in the landmarks table ovt_places_usa, assign the Overture ZIP code of the landmark to the range in table ip2city_dbiplite_probe_tbl . Note that this can be done independently of probing if the randomly selected address is selected in advance of probing, which it should be if it isn’t already. Note also that one node can route to multiple ZIP codes; this is common in rural areas. Duplicate the record in ip2city_dbiplite_probe_tbl and assign the additional ZIP code to the duplicate if it is found.
4.	Count the ip2city_dbiplite_probe_tbl ranges for which we have ZIP codes and those for which we don’t.
5.	Count the ZIP codes for which we have ranges and those for which we don’t (a complete list of ZIP codes is in table city2zip_tbl ).

Procedure
Steps 1 and 2 are done; the remaining work is steps 3 to 8, in order. Prerequisites: psql already connected to the right database, jq and curl on every machine that runs rdap-lookup.sh, and pip install duckdb only if parquet_to_pg.py is used.
1. Resolve hostnames to IPv4 (done)
python3 ovt_resolve_hosts.py resolve
It reads the first website of each place, looks up each distinct host once, and updates ip_address. The last run covered 7,911,403 hosts in about 22,200 seconds. It is resumable: Ctrl-C saves finished lookups, a rerun handles only new hosts, and --retry-failed retries earlier failures.
2. Reload the Overture data
2.a. Complete reload:
psql -X -c "TRUNCATE ovt_places_usa_ip_rdap" -c "UPDATE ovt_places_usa SET url_location = NULL WHERE url_location IS NOT NULL"
python3 ovt_resolve_hosts.py rdap --help | grep -- --random
The second command confirms you are in the directory holding the current ovt_resolve_hosts.py: it must print a line containing --random.
2.b. Delta (needed for production; not yet implemented)
The Overture data contains additions, deletions and changes at least daily. Write procedure to identify them relative to the current contents of ovt_places_usa and upsert/delete accordingly. Current contents of table should be archived for auditability in a clone of the table (the clone should include a timestamp with the archival date.
3. Run the full RDAP lookup
python3 ovt_resolve_hosts.py rdap
It covers 543,336 distinct IPs with 4 threads by default and is resumable. Expect about 20 hours (an estimate from one 0.54-second call, before any rate limiting). The default script path is ~/geo/rdap-lookup/cmd/rdap-lookup.sh. python3 ovt_resolve_hosts.py all chains steps 2, 6 and 7.
4. Produce the provider report
python3 ovt_resolve_hosts.py report
Prints every distinct url_location value with its row count and writes ovt_places_usa_url_location_counts.csv.
5. Flag providers as off-premises
Create a table (for which issue SQL code) and populate it with the records in the repo geo/overture_fetch/isp_categorization/definitive_isps.txt .
The current ovt_resolve_hosts.py should set onpremises as follows:
•	If status <> true, leave NULL
•	Else (if status = true):
•	Set onpremises = true if: {
o	registrant is an ISP (residential or business) AND there is no second registrant;
o	there is a match on one of the two RDAP ZIP codes;
o	there are two registrants and any non-ISP registrant’s RDAP ZIP code is adjacent to the landmark's Overture ZIP code (zip_adjacency table contains adjacent pairs in columns ZIP_A, ZIP_B) }
•	Set onpremises = false in all other cases (including where there are two registrants, one of which is an ISP, and the other’s ZIP code does not match or is adjacent to the landmark’s Overture ZIP code).
