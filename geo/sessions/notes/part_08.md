## Narrative

The slice opens mid-output from two commands Boris had already run: `rdap_registrant -fill -limit 200` (which logged 200 wide-range registrant lookups, mostly DoD/Amazon/USPS/A100 ROW blocks) and `psql -f geo/decomposition_exclusions.sql`, whose report listed 46 DoD-held allocations not yet covered by `geo_exclusions` plus a "WHAT THE POLICY COSTS" workload table of 40 registrants. ## Decisions and rationale

- **Landmark table name, key and index.** Instance: standardise on singular `landmark2zip_tbl` to match `dma2city_tbl`/`city2zip_tbl`; `PRIMARY KEY (organization, city, state_code)` because organization alone is not nationally unique; replace the invalid `USING ip` with a real index; add `CHECK (zip ~ '^[0-9]{5}$')` because 02301 Brockton loses its leading zero the moment anything treats ZIP as numeric. Boris accepted (implicitly — he moved on to modify other parts).
- **Do NOT duplicate probe rows per ZIP.** Boris's plan said duplicate `ip2city_dbiplite_probe_tbl` rows where several ZIPs map to one range. Instance refused on a hard constraint (see Traps). Replacement: `range2zip_tbl` keyed `(network, zip)`. Boris accepted — he later restated the multi-record idea and the instance pointed out it was already `range2zip_tbl`.
- **`zip` on the probe table stays the ip-api column.** Instance initially proposed landmark ZIPs live only in `range2zip_tbl`. Boris **modified**: keep `zip` as the probe's, add `zip_landmark`, and add `city_definitive`/`state_code_definitive`/`zip_definitive` populated from the `*_landmark` fields when non-null and from the probe fields otherwise. Instance implemented as STORED generated columns so they cannot drift.
- **`zip_landmark_count` added unrequested.** Rationale: without it, `zip_landmark IS NULL` conflates "no landmark found" with "several found that disagreed" — a conflation the instance said had cost the project time twice already. 0 = none, 1 = trustworthy, >1 = range spans several ZIPs and `zip_landmark` is NULL by design. Boris did not object.
- **City and ZIP counted separately.** Because Charter's `76.90.64.0/20` returns one city and three ZIPs, counting them together would discard a good city for a bad ZIP. Instance's choice; presented with the Hemet worked example.
- **Did not spend 91 minutes of Boris's ip-api budget on the exhaustive /20.** Instance ran the decisive enumerations from the sandbox's own budget and recommended against the production run because 15 of 16 /24s looked uniform. Boris did not insist; he redirected to a broader screen instead.
- **Decomposition unit: /25.** Instance recommended /24 (52-day cycle vs 104 days) with /25 deferred until the paid batch endpoint. Boris **overrode**: "The decision is /25." Instance implemented a `-unit` flag in `apply_splits` defaulting to 25, with `-unit 24` still available.
- **CDN/host exclusion rule.** Instance proposed `cdn_names` on correctness grounds (Akamai 02142 adjacent to MIT 02139 passes the adjacency test). Boris **rejected the framing**: the Akamai-at-MIT classification is a false *negative*, not a false positive, and in any case harmless because such a range never carries biddable retail traffic. Instance withdrew the proposal. Boris then **reinstated it on his own, stronger rationale**: all but the smallest cloud/CDN/host companies have private Internet access, so their last carrier node does not also route retail connectivity, making them worthless as landmarks. Instance implemented it as rule 2 ahead of the ZIP tests.
- **Rule ordering: provider test before ZIP tests.** Instance's reasoning: placed after the ZIP tests, any landmark near a provider's registered office passes (Akamai Cambridge, Cloudflare/Fastly San Francisco, Amazon Herndon). Boris accepted. One consequence the instance flagged and Boris did not overturn: a dealer at CarsForSale's own 57106 is now `false` via rule 2 even though Boris's stated intent would make it `true`.
- **ARIN-only operation; use `rdap-lookup.sh`, not `-follow`.** Boris: postcode and landmark arrangements differ per country and users want country-specific campaigns, so build one country at a time; the 303 on leaving ARIN's numberspace is the wanted signal. Instance accepted and dropped the queued RIPE entity-selection fix as unnecessary, noting the 867,905 "outside ARIN" rows are deliberately parked, not a backlog.
- **`mark` subcommand superseded.** It issued a plain UPDATE that the next `onpremises` run recomputed away. Rule 2 replaces it because it is a property of the registrant, not a per-row correction. Instance's call; Boris did not object.
- **Southwest Cyberport: added to `isp_names`, then removed.** Boris ordered it added (instance had found swcp.com is a real New Mexico ISP selling DSL, fibre and fixed wireless). The instance later argued against on the Synergy precedent — membership in `isp_names` bypasses the ZIP test entirely, so the ~81 nationally scattered hosted sites would flip to true. Boris **reversed himself**: "Southwest Cyberport removed from ISP table."
- **Synergy Networks: no action, in neither list.** Instance recommendation, after first (wrongly) recommending `isp_names` and then retracting it as the data came in. Derived standing rule: a name belongs in `isp_names` only if it routes retail AND does not host third parties; a mixed ISP-and-host belongs in neither list.
- **Do not build an RDAP address-text ZIP parser for bucket 6a.** Clean negative based on measurement (see numbers). Instance's call; Boris did not contest it.
- **No carrier node from BGP attributes.** Instance: `bgp_route_views.as_path` is NULL for every production row (ingester runs without `-per-peer`), and even with paths the second-to-last ASN is a whole company, so "landmark and subscriber share an upstream AS" says nothing about a ZIP; the geography lives in the node's reverse DNS. Boris **clarified that was never what he meant** — he wants the last carrier node read from mtr output for the random IP already selected for probing — and asked for the AT&T example to be explained.
- **Massachusetts throughput restriction.** Boris: "Yes, build and apply a temporary restriction to evaluate the throughput. Use Massachusetts (021xx ZIP codes)." Not yet built inside this range.

## Code, files, tables

- `geo/landmark2zip_tbl.sql` (merged `164513a`, reissued `254bf1b`). Creates `landmark2zip_tbl` (organization, street_address_1, street_address_2, city, state_code, zip text with `CHECK (zip ~ '^[0-9]{5}$')`, domain, ip inet, resolved_at, rdap_registrant, on_prem boolean, verdict; `PRIMARY KEY (organization, city, state_code)`; partial index on ip where not null, index on domain, partial index on on_prem). Creates `range2zip_tbl` (network cidr, zip, city, state_code, organization, landmark_ip inet, source default 'landmark', assigned_at; `PRIMARY KEY (network, zip)`) — the many-ZIPs-per-range record that replaces duplicating probe rows. Adds to `ip2city_dbiplite_probe_tbl`: `city_dbip`, `state_code_dbip`, `city_landmark`, `state_code_landmark`, `zip_landmark`, `zip_landmark_count integer`, plus `city_definitive`/`state_code_definitive`/`zip_definitive` as `GENERATED ALWAYS AS coalesce(<landmark>, <probe>) STORED`. Creates `ip2city_dbiplite_probe_tbl_network_gist` (`USING gist (network inet_ops)`) for the `network >>= $1` landmark→range lookup. Contains a refresh pass that sets `zip_landmark` only when a range has exactly one ZIP and `city_landmark`/`state_code_landmark` only when exactly one city, and sets count 0 for ranges with no landmark. ## Traps and gotchas

- **Duplicating probe rows per ZIP would permanently stop the pipeline.** `ip2city_dbiplite_history_tbl` requires `PRIMARY KEY (network, ran_at)` (enforced at runtime by an exception in `rebuild_probe_tbl.sql`). `check_geo_ip-api` writes `UPDATE ... WHERE network = $1 SET ran_at = now()`, and `now()` is fixed within a statement, so N duplicates of a network all receive an identical `ran_at`; the archive then inserts N rows sharing the key → PK violation → transaction rolls back → **the probe table never rebuilds again**. Fix: `range2zip_tbl` keyed `(network, zip)`.
- **`CREATE INDEX ... USING ip` is a syntax error** (`USING` names an access method, not a column). Boris's draft DDL would have created the table with no index and the error reads as harmless.
- **`PRIMARY KEY (organization)` silently rejects real landmarks** — "Lincoln County" exists in roughly two dozen states, so the second insert fails.
- **ZIP as a number destroys leading zeros.** 02301 Brockton had already appeared in the AS21928 data. The `CHECK (zip ~ '^[0-9]{5}$')` rejects `2301` and accepts `02301`; verified.
- **Adding a STORED generated column rewrites the whole table under ACCESS EXCLUSIVE** — tens of seconds on 2.09M rows. Same for building the GiST index (minutes). Both collide with `probe_batch`, so do not run "near five past the hour".
- **`coalesce(landmark, probe)` will assert an ip-api ZIP for a range known to span several.** The Hemet row ends up with `zip_definitive = 92543` for a /20 measured to carry three ZIPs. A consumer wanting only defensible ZIPs must require `zip_landmark_count <= 1`.
- **One random address per range makes the production table structurally blind to intra-range ZIP mixing.** If a range spans two ZIPs the probe picks one and the other leaves no residue — so the *absence* of observed mixing was never evidence of its absence. This invalidated the earlier reading of the "1 city, 3 ZIPs" result.
- **A comment the whole decomposition design rests on is wrong for ZIP.** `apply_splits` says "/24 is the right unit because it is the finest granularity ip-api expresses". True for city, false for ZIP: `76.90.65.0/24` splits at /25 and `45.19.184.0/24` only becomes uniform at /29.
- **ip-api ZIPs drift faster than a probe cycle.** 3 of 16 fixed Charter wireline addresses changed ZIP in two days, on the operator previously proposed as the *stable* control against mobile drift. A 52-day (/24) or 104-day (/25) cycle cannot track that.
- **`dig` is not installed in the sandbox, and the failure is silent.** The first reverse-DNS test returned no PTRs anywhere and appeared to confirm Boris's unassigned-address hypothesis; redone with Python's resolver, all 128 addresses had PTRs and the conclusion reversed. The instance explicitly flagged the void result as its own, not the data's.
- **`/tmp` does not persist between sandbox tool calls.** A seeded resume file vanished and the tool began probing for real; one call was killed by a 300-second timeout for this reason. Fix: do seed-and-run in a single call.
- **Two copies of every Python script, and `deploy.sh` does not cover Python.** `~/geo/overture_fetch/ovt_resolve_hosts.py` was a stale working copy; the repo copy is `~/geo/src/claude/geo/overture_fetch/`. Boris's `onpremises` run was grinding through 36 chunks recomputing the *old* rule, which is why every chunk reported `0 changed`. Tell-tale: the dry run printed `2a/2b/3/4/5a/5b` and no provider line. Same hazard exists for `rdap-lookup.sh` (a second copy under `~/geo/` while `geo/main.go` defaults `-rdap-script` to `./rdap-lookup.sh`), and the `~` in that default needs shell expansion, which Python's `subprocess` without `shell=True` will not do.
- **`mark` was not durable.** `cmd_mark` issued a plain `UPDATE ... SET onpremises = false`; `cmd_onpremises` then recomputed the column for every `lookup_status='true'` row with no exemption, flipping marked rows back.
- **`isp_names` membership bypasses the ZIP test entirely.** Rule 3a makes a single-ISP registrant a hard `true`, so adding a mixed ISP-and-host (Synergy, Southwest Cyberport) would flip all its nationally scattered hosted sites to true. For Southwest Cyberport the stored column was still *stale* (only dry runs had been done), so the damage would have appeared only on the first real run — 186 good anchors kept either way, 81 pure loss.
- **A CDN's registered office can sit in the same or an adjacent ZIP as a real landmark**, so the adjacency test alone cannot reject it: Akamai 02142 vs MIT 02139, Cloudflare 94107 vs San Francisco landmarks, Amazon 20171 Herndon vs Herndon/Reston/Ashburn. `cityofchicago.org → Cambridge MA` is an obvious reject; `mit.edu → Cambridge MA` is a silent pass.
- **Section 2 of provider_names.sql groups by `registrant_1` only, while the ZIP tests also consider `registrant_2`** — so a row can be true because the second registrant matched while the first is a host. Section 4 was added to name the deciding registrant.
- **A high `places` count signals hosting but never proves it.** Northwestern Memorial's 855 are real clinics and departments under one system; CarsForSale.com's 131 are its dealer customers. Only geographic spread separates them, hence the zip3-spread detector.
- **`rdap-lookup.sh` exits 1 on ARIN HTTP 303** for all early-registration space (Apple 57.x, 51.x, 151.x, 46.x). `rdap-lookup-follow.sh` follows the redirect but on RIPE space returns *maintainer* objects with no address (`APPLE-MNT`, `CC72744-MNT`, `RIPE-NCC-LEGACY-MNT`, all `NOT_POPULATED`), which land as rule 6a `false`. Boris's ARIN-only decision makes the 303 the wanted signal, so the 867,905 "outside ARIN" rows are parked by design — worth recording in the readme so nobody "fixes" it by switching scripts and silently pulls in RIPE space.
- **RDAP addresses can be present and wrong, which is worse than absent.** `C01840002` gives "2612 Edison Avenue, Ft Myers, FL, 32204" — 32204 is Jacksonville, 300 miles away — and a wrong-but-present ZIP passes rules 4/5 against the wrong place rather than failing safe. `SYNERG-62` has street and state with a blank ZIP.
- **ARIN serves Canada**, so 85% of bucket 6a carries postal codes like `M5V 3A8` that can never match a US ZIP. Those rows are correctly and permanently `false`.
- **An ISP's own name appears in its customers' ARIN records.** Of eight ARIN orgs matching "Synergy Networks*", only `SYNN` is Synergy's own; three are downstream business premises SWIPed with the ISP's name (Naples Beach Hotel & Golf Club; "Synergy Networks - Brown and Brown") and one is an unrelated Kansas City company. Netname distinguishes the roles (`UU-63-75-167` hosting vs `SYNN-2075` own space) but the pipeline keys on registrant, and netnames reflect which upstream allocated the block, not which business unit uses it.
- **Fan-out guard is mandatory for the carrier-node method.** A regional aggregation router or MPLS egress that is the penultimate hop for a whole metro would fan one landmark's ZIP across thousands of unrelated ranges, or fifty ZIPs onto one range. The bound must be measured from the histogram, not guessed; it currently sits at 1 as the only value unambiguous by construction.
- **`bgp_route_views.as_path` is NULL in production** because the ingester runs without `-per-peer`, and even populated it would be useless for geography: AS7018 is AT&T in fifty states.
- **Four things could not be reused from the range path in `landmarks` mode**, each a silent-failure mode if ignored: retries must re-trace the same address (the range sampler would have recorded it in `tried` and failed attempt two with "range exhausted", capping every landmark at one try); output must be keyed on the address (the existing table is `ON CONFLICT (network)` and many landmarks share a prefix, so each would overwrite the last leaving one arbitrary survivor, raising nothing); targets must be DISTINCT addresses (takes the pass from ~1.2M traces to ~123k); `-pause-file` must stop the feeder, not the workers.
- **Attachments did not reach the instance at all.** A `.docx` arrived as raw binary, a `.pdf` and a `.txt` produced no content and no new commit. Three failures in a row; the working route was committing to the repo (`geo/sessions/`).
- **UI elapsed-time counters are unreliable.** Boris saw "162 minutes" for a python3 script; nothing was running, and the sandbox container is recreated per command so no process can survive between calls even in principle.
